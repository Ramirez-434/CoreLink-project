1. Vulnerabilidade Selecionada e Priorização

Vulnerabilidade Mitigada

Vulnerabilidade 2 (Ataque de Duplo Clique / Concorrência de Checkout): No formulário de faturamento (/checkout), o botão permanecia interativo durante a requisição assíncrona, permitindo múltiplos disparos simultâneos.

Justificativa Técnica: Em operações de faturamento e emissão de pedidos B2B, a janela entre o primeiro clique do usuário e a resposta da requisição assíncrona (ou o intervalo de microssegundos anterior à re-renderização do DOM pelo React) permitia que cliques repetidos disparassem execuções concorrentes de createOrder. Além disso, em um ataque de concorrência direta (*Race Condition / Time-of-Check to Time-of-Use — TOCTOU*), duas requisições que chegassem ao servidor no mesmo milissegundo podiam ultrapassar uma verificação simples de leitura e gravar pedidos duplicados ou consumir duas vezes um cupom de uso único.

2. Resultado Esperado e Comportamento Alcançado

Mutex Anti-TOCTOU Ativo

O fluxo de checkout (CheckoutForm.tsx e src/actions/order.ts) recebeu 4 barreiras de proteção contra concorrência: (1) Trava Síncrona (checkoutLockRef) que neutraliza cliques em menos de 1ms; (2) Controle de Estado (isLoading) que desabilita botão, cupom e checkbox LGPD com disabled e pointer-events-none; (3) Chave de Idempotência (idempotencyKey) única por sessão de checkout; e (4) Mutex em Memória (activeCheckoutLocks) + Incremento Condicional Atômico (tx.coupon.updateMany) no servidor, garantindo que rajadas paralelas no mesmo milissegundo abram apenas 1 transação no PostgreSQL.

6.1 Mutex Anti-TOCTOU e Cupom Atômico (src/actions/order.ts)
export async function createOrder(
  productId: string, couponId?: string, idempotencyKey?: string
): Promise<CheckoutResult> {
  const userId = session.user.id as string;
  const lockKey = `${userId}:${productId}`;

  if (idempotencyKey && processedIdempotencyKeys.has(idempotencyKey)) {
    return { success: true, orderId: processedIdempotencyKeys.get(idempotencyKey)!.orderId, deduplicated: true };
  }
  // Mutex contra Race Condition (TOCTOU) em chamadas simultâneas (0ms)
  const inFlightPromise = activeCheckoutLocks.get(lockKey);
  if (inFlightPromise) {
    const firstResult = await inFlightPromise;
    return { ...firstResult, deduplicated: true };
  }
  // Incremento atômico condicional dentro de prisma.$transaction:
  const updated = await tx.coupon.updateMany({
    where: { id: coupon.id, isActive: true, usedCount: { lt: coupon.usageLimit } },
    data: { usedCount: { increment: 1 } },
  });
  if (updated.count === 0) throw new Error("COUPON_INVALID");
}

7. Roteiro de Validação e Testes de Segurança (Homologação)

Cenário de Teste Procedimento Executado Resultado Obtido na Homologação
Ataque de Duplo Clique Rápido em /checkout Executar 5 cliques rápidos no botão "Confirmar Pedido" após marcar o aceite LGPD. O 1º clique acionou checkoutLockRef e desabilitou o botão ("Processando Pedido..."); os 4 cliques seguintes foram bloqueados na UI.
Disparo Concorrente via Rede (TOCTOU 0ms) Disparar 3 requisições paralelas (Promise.all) direto para createOrder no mesmo milissegundo. O mutex activeCheckoutLocks interceptou as requisições #2 e #3 em voo, abrindo apenas 1 transação no PostgreSQL.
Retransmissão com Mesma idempotencyKey Reenviar requisição com o mesmo token idempotencyKeyRef após a conclusão do pedido. O cache processedIdempotencyKeys e a janela de 15s retornaram o pedido existente (deduplicated: true).
Concorrência em Cupom de Uso Único Submeter simultaneamente duas compras utilizando cupom com usageLimit = 1. A cláusula atômica updateMany({ usedCount: { lt: usageLimit } }) garantiu que o limite jamais fosse ultrapassado.
